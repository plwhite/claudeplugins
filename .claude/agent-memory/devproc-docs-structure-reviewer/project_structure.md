## tests/ layout (post move-tests-out-of-plugin, #50, 2026-08-12)

- `devproc/tests/` moved wholesale to `tests/devproc/`. Driver: `devproc/` is the **unit of distribution** (marketplace source, the tree `docker/Dockerfile` copies, what `docs/setup.md` installs), so test material inside it shipped to every consumer. Remember this boundary — anything inside `devproc/` is read by consumers, anything outside is maintainer-only.
- `tests/devproc/` holds four peer directories: three fixture suites (`feature-spec-reviewer/`, `feature-design-reviewer/`, `internal-docs-reviewer/`) each with its own `README.md`, plus `harness/` (`run.sh`, `README.md`, `.gitignore` = `out/`).
- The `tests/devproc/` (not bare `tests/`) shape is deliberate — leaves room for tests of other plugins/areas. Rationale lives only in `features/plans/move-tests-out-of-plugin.md` "Why `tests/devproc/` and not `tests/`", not in any live doc.
- `harness/run.sh` covers only the two plan-file suites; `internal-docs-reviewer` is deliberately excluded (its cases are fixture *directories* reviewed as a stand-in repo root, needing a different invocation shape). Stated in harness/README.md and the script's error path, not in the internal-docs-reviewer suite README.
- Surfaced from: root `README.md` `## Documentation` table (row now links `tests/README.md`), root `CLAUDE.md` `## tests directory` section, `devproc/README.md`'s three agent-reference lines, and `CONTRIBUTING.md` (re-run-the-suite bullet).
- `tests/README.md` (added 2026-08-12, 36th review) is the area index: what it is + why outside `devproc/` + `tests/devproc/` namespacing rationale, a "Start here" harness pointer, a four-row Contents table (3 suites + harness), and an "Adding a suite" maintenance rule mirrored by an equivalent rule in root `CLAUDE.md` `## tests directory`. No `tests/devproc/README.md` — the intermediate level is deliberately un-indexed.
- Harness invocation appears in FOUR path forms across docs (repo-root `tests/devproc/harness/run.sh` in tests/README.md + devproc/README.md; suite-relative `../harness/run.sh <suite>` in both plan-file suite READMEs; `./run.sh` in harness/README.md). Only harness/README.md states the script is location-independent ("Run from anywhere").

## Workspace terminology (post features-outside-repo, #60, 2026-08-22)

- **Controlled vocabulary, defined once** in `FEATUREMODEL.md` `### The workspace` (both copies): **workspace** = the directory holding `CLAUDE.md`, `NOTES.md`, `features/`; **tracked workspace** = the workspace IS a git repository root; **untracked workspace** = a plain dir with one or more repos beneath it. Feature tracking always lives at the TOP of the workspace, never inside a nested repo.
- Behaviour keyed to it: `/feature-init` step 5 writes `.gitignore` only when tracked (guard = `git rev-parse --is-inside-work-tree`), and in an untracked workspace neither reads nor edits `.gitignore`; `/feature-spec` step 1a runs `git remote -v` inside the repo the issue belongs to, with a five-case resolution rule (tracked / one beneath / several→ask / none→ask / no GitHub remote→ask), always naming the repo it read.
- `$CLAUDE_PROJECT_DIR` is now glossed "(the workspace root)" — NOT "the repository root" — in `docs-structure-reviewer.md`, `internal-docs-prune/SKILL.md`; and `internal-docs-reviewer.md` L14 + `internal-docs-prune/SKILL.md` L42 say "the workspace root" for the review scope.
- **Definition surfaces (as of the 37th review, 2nd pass — all landed):** `FEATUREMODEL.md` `### The workspace` (canonical, now placed immediately after the intro and *before* `### Sign-off criteria`, lead sentence + two bullets + an "exhaustive" paragraph); `docs/workflow.md` `## Where the workspace is` (user-facing, anchor `#where-the-workspace-is`, linked from L12 and from setup.md); `docs/setup.md` `### Initialise devproc in each workspace for which you want to use it` (one-sentence definition + link to workflow anchor); `devproc/README.md` `## Setup` first paragraph (definition + links to both). All four `devproc/README.md` conditionals read "git-ignored in a tracked workspace".
- **Where the vocabulary still has NOT reached (2nd pass):** root `README.md` (Documentation table, never mentions it — declined SUGGESTION), `docs/capabilities.md`, `docs/container.md` ("the project directory", no equivalence sentence — declined MINOR), `docs/workflow.md` L191 ("Open Claude in the project directory", one screen below its own workspace definition), `docs/setup.md` `.claudeignore` step (mixes "each project" / "each workspace" / "each project root").
- **Deliberate wording exception, do NOT flag:** `feature-init/SKILL.md` step 5's heading says "where the workspace is a git repository" rather than "tracked" because the heading precedes the inline definition; the skill also carries a parenthetical explaining why it restates the definition instead of referencing `FEATUREMODEL.md` (the skill is what installs that file).

## Conventions observed

- Plugin layout: `.claude-plugin/plugin.json` + `skills/<name>/SKILL.md` + `agents/<name>.md`
- SKILL.md frontmatter: name, description; optionally argument-hint, disable-model-invocation
- Agent frontmatter: name, description (multi-line w/ examples), tools, model, color; optionally memory
- Feature list files use `###` headings with `[slug]` tags; COMPLETED headings end with YYYY-MM-DD
- bin/ = 4 wrapper scripts (claude-build/run/attach/stop); docker/ = Dockerfile + baked config; both inventoried in CLAUDE.md ## Container mode
- Out-of-scope for audits: historical plan files under `features/plans/*.md` and `.claude/agent-memory/` snapshots retain old names/paths as point-in-time records.

## Plan-file schema, post clear-specs-and-designs (#57, 2026-08-12)

- Plan-file sections now: Handoff / **Requirements** (input, captured faithfully, deliberately NOT held to `### Readability` — reorganising a user's own words is how their meaning is lost) / **Spec** (new — what the feature must do, written to stand alone, IS held to `### Readability`; agreed at `/feature-spec`) / Sign-off strategy / Design (must open with an overview before any detailed section) / Sub-tasks / Review record.
- `### Readability` (new canonical subsection of `features/FEATUREMODEL.md`, alongside the pre-existing `### Sign-off criteria`) is the single statement of "what readable prose looks like" for specs/designs: two outcome statements (spec followable with no background on the feature; design followable by someone who knows only requirements+spec) over a set of structural tests (Point first / Nothing assumed / Unambiguous / Detail subordinated / Rationale without detour / Proportionate) — outcome wins where they disagree. Both `feature-spec-reviewer` and `feature-design-reviewer` reference it (never restate it) via a MAJOR `[rewrite]` Clarity criterion, and both agents' pre-existing "stylistic preference capped at MINOR" constraint was qualified to state that a `### Readability` failure is a different category, not a severe case of taste.
- `/feature-design` gained a **spec-amendment route** (its own step, separate from the near-identical review-block steps 7/8 it deliberately shares with `feature-spec`): design work may reveal the spec is wrong/impossible, `/feature-design` may then edit `## Spec` but never silently — user approval required, logged as its own `## Review record` line. In **unattended mode** this is a **second, independent stop condition** alongside the existing "verdict must be READY + no [decision]" gate — a proposed amendment stops the run regardless of verdict, because no verdict string can express "the spec itself changed". Documented consistently in `feature-design/SKILL.md` (step 7f bullet + step 9d), `docs/workflow.md` ("The three modes" → Unattended bullet, last sentence), `dev-process-manager.md` (step 1), `devproc/README.md`.
- `docs-structure-reviewer.md`'s own Criterion 5/6 (Clarity vs Stylistic Consistency) was actively split as *part of* #57 to fix a worse conflation (MINOR previously defined as "clarity or consistency issue"; stylistic-preference cap previously carved out "unless they cause genuine confusion") — NOTES.md L262-298 has the full writeup. Current wording is deliberate/current, not stale. Residual (SUGGESTION, dismissed by the feature itself, not urgent): this agent's Criterion 5 is still an independently-worded definition from `### Readability`, with no shared source between the two — watch for drift over time.
- Both reviewer-agent test suites (`tests/devproc/{feature-spec-reviewer,feature-design-reviewer}/`) are built on a byte-identical-across-files shared baseline (`control.md`'s `## Requirements`/`## Spec`/`## Sign-off strategy` text copied into every case in both suites) — a wording weakness in the baseline fails cases nondeterministically since a MAJOR-capable Clarity criterion checks every section of every fixture. Both suite READMEs now carry a "Maintaining the shared baseline" subsection explaining this. 7 spec-suite cases, 8 design-suite cases as of #57 (design suite has an extra `no-spec` case testing the missing-`## Spec` guard; spec suite deliberately does not, an accepted gap recorded in `features/plans/clear-specs-and-designs.md` Sub-task 11).
