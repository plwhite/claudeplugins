## Requirements

From issue #42, "Delete the demo plugin" (verbatim):

> The demo plugin was really just present to make sure that plugins worked in this context. It is still there, but that is honestly a bit pointless - we should delete it completely.

### Scope clarification: what "completely" requires

"Delete it completely" means the feature is done only when the `demo/` plugin is
gone **and** no *live* reference to it remains in the repository — no dangling
links, no manifest entries pointing at a missing directory, no current
documentation describing a plugin that no longer exists. Removing the directory
alone is not sufficient.

"Live" is the operative word: historical feature records that mention demo as
part of already-completed work are **not** rewritten (see "Not in scope" below).
Scrubbing them would falsify this repo's durable record of past features, which
runs against the whole point of the `features/` split. (Confirmed with the user
at spec sign-off, 2026-07-24: history is left intact; only live references are
removed.)

The following reference sites are known to exist at spec time (informational —
the exact edits are for `/feature-design` to plan; there may be others a fresh
scan turns up):

- `demo/` — the plugin directory itself (manifest, `demo-skill`, `demo-agent`, README).
- `.claude-plugin/marketplace.json` — a `{ "name": "demo", "source": "./demo" }` entry in the `plugins` array.
- `README.md` — a row in the Plugins table (`| [demo](demo/README.md) | … |`).
- `CLAUDE.md` (project instructions) — the `## demo plugin` section.
- `NOTES.md` — a note that the container Dockerfile COPYs `demo/` (already stale: the current `docker/Dockerfile` copies only `devproc` and `.claude-plugin`, not `demo`); worth correcting or removing so it does not mislead.

Not in scope (records of the past, not live pointers):

- `.claude/agent-memory/` files mention demo, but agent memory is regenerated by the agents themselves and is not hand-edited.
- Historical feature records that reference demo as part of completed work — `features/COMPLETED.md`, `features/plans/plugin-documentation.md` (a completed feature whose subject *was* documenting the demo plugin), `features/plans/claude-container.md`, and other past plan files. These record history and are not rewritten.
- This feature's own entry in `features/PENDING.md` references `demo/` and `delete-demo-plugin`; it is carried through the normal lifecycle to `features/COMPLETED.md` by `/feature-end`, not removed by the deletion edits.

## Sign-off strategy

This is a low-risk deletion of a deliberately trivial plugin plus its references
— configuration and prose only, no product logic. The bar per category (model
defined in the project CLAUDE.md `### Sign-off criteria`):

- **Testing** — Manual verification only; there is no automated test suite for plugin wiring in this repo. Bar: after the deletion, a repository-wide search confirms no remaining `demo` references in live configuration, docs, or the current feature list — i.e. excluding regenerable agent memory and the historical feature records listed under "Not in scope" — and `.claude-plugin/marketplace.json` remains valid JSON listing only real plugin sources. No automated tests added.
- **Documentation** — Updating the docs *is* part of the deletion, not a separate follow-up: the root `README.md` Plugins table and the `CLAUDE.md` `## demo plugin` section must be removed. Bar: all user-facing and project docs updated so none describe or link to the demo plugin.
- **Code review** — User reviews the full diff. The change is small and mechanical; a single human read of the diff is proportionate. No agent code-review pass.
- **Docs review** — `docs-structure-reviewer` over the changed documentation (root `README.md`, `CLAUDE.md`), to confirm the removals leave no broken links or orphaned references in the doc hierarchy. This is the sign-off most likely to catch a dangling pointer, which is the main risk of a "remove references everywhere" change.
- **User review** — The user confirms the demo plugin is gone and nothing else broke.

## Design

A pure deletion. No product logic is involved; the whole feature is removing the
`demo/` directory and editing the handful of files that point at it, leaving the
repository internally consistent (no broken links, valid manifest).

Approach (documentation references first, then the directory + manifest):

1. **Remove the documentation references.** Three doc touch-points:
   - `README.md` — delete the `| [demo](demo/README.md) | … |` row from the
     Plugins table (keep the table and its `devproc` row).
   - `CLAUDE.md` — delete the entire `## demo plugin` section (its heading and body).
   - `NOTES.md` — the note claiming the Dockerfile COPYs `demo/` is already
     stale (the Dockerfile copies only `devproc` and `.claude-plugin`). Correct
     it so it no longer implies a `demo/` copy step, rather than leaving a note
     that references a directory that will no longer exist.

2. **Remove the plugin and its manifest pointer together.** Delete the `demo/`
   directory (`git rm -r demo`), and remove the `{ "name": "demo", "source":
   "./demo" }` object from the `plugins` array in `.claude-plugin/marketplace.json`,
   leaving `devproc` as the sole entry. These belong in one step because a
   `demo/` directory with no manifest entry, or a manifest entry with no
   directory, is a broken intermediate state — the manifest and the directory
   must move together.

**Ordering — why docs first.** Removing the documentation references before the
directory means the repository never holds a dangling link: after step 1 the
docs no longer point at `demo/`, so step 2 can delete the directory without
leaving a 404 link in `README.md`/`CLAUDE.md`. The reverse order would leave a
transient dead link between the two sub-tasks. The manifest+directory atomicity
of step 2 is preserved either way, so docs-first is strictly cleaner.

Verification is a repo-wide **word-boundary** search for `demo` (`\bdemo\b`,
case-insensitive), expecting hits only in the out-of-scope sets named in
Requirements — regenerable `.claude/agent-memory/`, historical feature records,
and this feature's own tracking entry/plan. A word-boundary match keeps the
check crisp (it will not fire on incidental words such as "demonstrate").
Anything outside the out-of-scope sets is a missed live reference.

**Why two sub-tasks, not one:** the split mirrors the two sign-off surfaces —
sub-task 1 is the documentation the `docs-structure-reviewer` pass covers,
sub-task 2 is config the manifest must stay valid across — and keeps each
sub-task's completion check independently auditable. Both are small.

Out of scope (settled at spec): historical/records references are left intact;
the container `docker/Dockerfile` needs no change (it never referenced demo).
