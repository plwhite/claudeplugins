## Requirements

From issue #47 — "Tendency for Claude to leave final sign off as a non-subtask" (verbatim):

> Claude routinely creates multiple subtasks without user review, then puts significant user review into a feature level signoff. This review should be an explicit subtask, to make the flow clearer and reduce risk of it not being properly done.
>
> The best way to do this is that if there are final feature signoff criteria, then they should be presented as a checklist just like other subtasks. In other words, the final subtask becomes "final signoff criteria" in every case, with whatever the signoff criteria are, and has explicit checklists for whatever the actions are (run a full code review, user review, user end to end testing, whatever).

(Issue has no comments.)

### Interpretation and scope notes

- The behaviour to change lives in the `devproc` plugin. The current model (project `CLAUDE.md`, `### Sign-off criteria`) explicitly permits a **feature-level sign-off** recorded once in `## Sign-off strategy` "rather than repeated on every sub-task" (e.g. one end-of-feature docs review or `/review-branch`). This feature reverses that guidance for *final* sign-offs: where such criteria exist, they must surface as an explicit final sub-task with a checklist, not live only in the strategy prose.
- Primary artefacts likely affected: the sign-off model in project `CLAUDE.md`; `devproc/skills/feature-design/SKILL.md` (which builds the sub-task list and per-sub-task checkboxes); possibly `devproc/skills/feature-spec/SKILL.md` (sign-off strategy wording), `devproc/skills/feature-end/SKILL.md` (which closes the feature and would gate on the final sub-task), and `devproc/agents/feature-design-reviewer.md` (so the reviewer checks the final sub-task exists). Exact set to be resolved in `## Design`.
- The final sub-task's checklist items are ordinary sign-off checkboxes and must obey the existing auditability and named-performer rules (every review sign-off names its performer — agent or user).
- **Self-application:** this feature is itself the one teaching the workflow to surface final sign-offs as an explicit sub-task, so its own design should apply its own rule to its own final sub-task.

### Settled decision (user, 2026-07-25)

- **Conditional, not mandatory.** A "final sign-off criteria" sub-task is created **only when final feature-level sign-off criteria genuinely exist**. If there are no end-of-feature sign-off items and that has been explicitly agreed, no such sub-task is created — an empty placeholder is never added.
- **Governing objective:** *no sign-off items that are not explicitly in the list of items to do.* Any sign-off that would gate feature completion must appear as an explicit checkbox in a sub-task's list; it must not live only in the feature-level `## Sign-off strategy` prose where it can be skipped or done cursorily. The final sub-task exists to give such end-of-feature sign-offs a concrete home — and if there are none, there is nothing to home and the sub-task is omitted.
- This resolves the earlier design fork against the issue's literal "in every case"; the narrowing is deliberate and agreed, and keeps the model consistent with its own rule that a box which can never be ticked must never be written.

## Design

### The mechanism

The `devproc` workflow already lets an end-of-feature sign-off live *only* in the
plan's `## Sign-off strategy` prose ("a feature-level sign-off … is recorded there
too, rather than repeated on every sub-task"). That is the exact wording issue #47
wants reversed, because a gate recorded only in prose is easy to skip or do
cursorily.

The change keeps `## Sign-off strategy` as the place that records the **bar** (the
policy: "one `/review-branch` before end", "one `docs-structure-reviewer` review",
"final user review"), but requires `/feature-design` to **materialise** any such
end-of-feature/final gates as an explicit final sub-task named **"Final sign-off
criteria"**, one checkbox per gate. Strategy = policy; the final sub-task = the
actionable, auditable checklist. This satisfies the governing objective — *no
sign-off item that gates completion lives only in strategy prose*.

Per the user's settled decision, the final sub-task is **conditional**: it is added
only when the strategy actually defines end-of-feature gates. A feature whose
sign-offs are all satisfied within earlier sub-tasks gets no final sub-task, so we
never write an empty checklist that can never be ticked.

### Design decision D1 — how `/feature-end` reconciles with the final sub-task

The tension: `/feature-end` today *performs* the close-out docs review (its step 4)
and requires every sign-off box ticked (its step 2). If the docs review is now a box
in the final sub-task, that box cannot be pre-ticked at step 2, because the review is
run during step 4 — and the docs review must run against the near-final state.

**Decision:** the "Final sign-off criteria" sub-task is the checklist of close-out
gates, and `/feature-end` is where the close-out-only boxes are performed and ticked.
Concretely:

- Boxes that do not need final-state docs — e.g. `/review-branch` code review, user
  review, the manual dry-run — are performed as the last work **before** running
  `/feature-end`, and must be ticked before it starts.
- The **docs-review box** is performed **by** `/feature-end` (its existing step 4),
  which ticks that box as it runs — the single review already run there *is* that box,
  so there is no second review.
- `/feature-end`'s step-2 completeness check is reworded to exempt the box(es) it
  performs itself: all other sub-tasks and all other final-sub-task boxes must be
  ticked before it starts; the docs-review box is satisfied during the run.
- So the model (Sub-task 1) and `/feature-design` (Sub-task 2) must have designers
  **annotate** any `/feature-end`-performed box "(performed at `/feature-end`)", and
  must tell `/feature-checkpoint` and resuming sessions that this one annotated box
  being unticked before close is expected — not an incomplete feature. Without this the
  exemption would have to be inferred by category alone, and a perpetually-unticked box
  would read as unfinished work.

**Rejected alternative (Alt B):** perform *all* final-sub-task boxes (including docs
review) before `/feature-end`, leaving `/feature-end` a pure verify-and-move. Rejected
because it discards `/feature-end`'s deliberate "review sees the feature in its final
completed state" ordering (step 3 moves the entry to `COMPLETED.md` before the review),
and would force the docs review to run against not-yet-final docs. Keeping
`/feature-end` as the performer of the last, order-sensitive box is the smaller, safer
change. **Not expanding `/feature-end`'s scope** to newly *run* `/review-branch` or
originate the user review is deliberate — the issue asks to make the gates explicit,
not to relocate where they are performed.

done first and the derived skills/agent follow. Between sub-tasks the prose is
transiently inconsistent (model updated before a skill that cites it) — unavoidable for

sign-off sub-task's `/review-branch` and `docs-structure-reviewer` passes catch any
residual drift. Fixtures (Sub-task 5) follow the reviewer change (Sub-task 4) that
breaks them.
